# StepWise optional S3 artifact storage — implementation specification

Status: **design only; implementation and validation not yet completed**.

## Why this fits the existing code

Currently `src/stepwise/storage.py` publishes attempt artifacts with a same-filesystem staging-directory rename. `src/stepwise/api/main.py` serves generated downloads with `FileResponse(store.resolve(key))`. `src/stepwise/jobs.py` instantiates `ArtifactStore(settings.artifact_root)`. This works with the Compose shared volume but does not support independently scheduled API and worker containers without shared disk.

## Scope (reviewable phases)

1. Preserve the existing local store as default. Add an `ArtifactBackend` protocol supporting `put(id,name,bytes)`, `publish(id,token,artifacts)` and `read(key)`. Add a factory selected by `STEPWISE_ARTIFACT_BACKEND=local|s3`.
2. Add an opt-in S3-compatible backend using boto3 with a configurable bucket/endpoint/region/credentials. Use generated keys `<analysis UUID>/<attempt UUID>/<safe filename>` and reject traversal. Upload each object before passing artifact keys to `AnalysisRepository.finish()`. Verify object existence and size; do not treat S3 ETags as universally valid MD5 checksums. Preserve the existing database ownership/fencing checks.
3. Change only the download adapter to serve bytes/streamed file-like data from the backend; continue gating generated content on the analysis `SUCCEEDED` state, without disclosing storage keys or unauthenticated presigned URLs.
4. Add an optional MinIO Compose profile and document local-only development credentials. Keep the shared-volume default untouched and use a separate test DB when switching storage backend because old storage keys are not migrated.
5. Add isolated tests with a fake S3 client, plus a live MinIO integration test that is skipped when the service is unavailable. Exercise traversal, partial upload, stale token after recovery, duplicate delivery, and storage outage. Add a two-API/two-worker synthetic end-to-end smoke run.
6. Only after S3 tests pass, consider separate Kubernetes/kind deployment PR. Do not mix Kubernetes setup into this first implementation.

## Critical correctness and security requirements

- S3 does **not** support atomic directory rename or a transaction shared with PostgreSQL. Objects may exist even if DB finalization fails. Report publication is a database operation, not an S3 atomic operation.
- Interrupted uploads can leave orphans. Do not implement blind deletion; a future cleanup job must check current DB references and a retention window.
- No claim of exactly-once computation, automatic worker resurrection, cross-host HA, or public production readiness.
- Unavailable storage should lead to a bounded safe error, not a 500 exposing credentials, bucket, endpoint, file paths, or untrusted object bytes.
- Keep uploads bounded and key names generated by application logic; local and S3 modes should behave identically at the API boundary.
- Use only synthetic sample recordings, with no paid cloud service required.

- [ ] Postgres transaction and token fencing prevent partial/obsolete outputs becoming visible.
- [ ] Live MinIO synthetic end-to-end succeeds and downloads match expected bytes.
- [ ] Two API instances and two worker processes function without sharing an artifact filesystem.
